## 关键调研结论：抖音 / 小红书有没有开放接口？

**结论：两家都"有开放平台"，但都拿不到任意博主的笔记/视频内容。原方案里"直接读取博主合集"这一步，1.0 做不到。**

| 平台 | 官网 | 实际开放了什么 | 能不能取博主合集 |
|---|---|---|---|
| 抖音 | `open.douyin.com` / `developer.open-douyin.com` | 小程序、移动/网站应用、直播小玩法；内容侧有「查询**授权账号**视频列表」（Scope `video.list`，需用户授权+申请权限） | ❌ 只能取**已授权给你的账号**；小程序「获取作者视频列表」也需**作者本人授权给该小程序** |
| 小红书 | `openaccount.xiaohongshu.com` | 只有**账号登录**能力（OAuth 2.0 + `basic_info` 用户基本信息） | ❌ 官方 API 里**没有任何笔记/内容接口** |
| 小红书 | `open.xiaohongshu.com` | **电商开放平台**（商品/订单/物流，面向商家 ERP） | ❌ 与内容无关 |
| 小红书 | 蒲公英 | 品牌 × 博主的**商务合作平台** | ❌ 不是面向第三方 App 的开放接口 |

> ⚠️ 网上大量"小红书笔记详情 API / 抖音作品 API"教程，多为第三方爬虫/灰产接口，违反平台协议、不稳定、易被封且有法律风险。**方案里不采用。**

### 应对：内容来源改为「导流为主、自建为辅」

| 方案 | 做法 | 版权/合规 | 1.0 建议 |
|---|---|---|---|
| A. 自建内容池 | 平台自己产出 / 签约少量博主共创妆教 | ✅ 最干净 | ✅ 用作样板数据 |
| B. 官方授权接入 | 与博主签授权，走抖音 OAuth 拉合作博主内容 | ✅ 合法，但一对一谈 | ⏸ 二期 |
| C. 标签导流 | 平台只存"博主 + 风格标签 + 跳转链接"，点进去到抖音/小红书看原作 | ✅ 风险最低 | ✅ **1.0 主用** |
| D. 用户自备链接 | 用户粘贴链接，平台只生成学习清单 | ⚠️ 灰区 | ❌ 不建议 |

**改后架构**：`fetch_creator_collection` / `get_tutorial_breakdown` 不再调平台 API，改为**查平台自建内容库**；库里对每个博主只存**风格标签 + 合集索引 + 官方跳转链接**（方案 C），妆教拆解由平台用自己的知识库生成，**不复制、不搬运原视频**。

### 追问：能不能让用户在 CLI 里「搜索 + 拉取」？

| 动作 | 能不能做 | 说明 |
|---|---|---|
| 搜索 | ✅ 能 | 但搜的是**你自己平台的博主索引库**（运营录入的「博主 + 风格标签 + 合集」），不是抖音/小红书的实时搜索 |
| 跳转 | ✅ 能 | 展示官方链接，用户点开去原平台看原作 |
| **拉取内容**（未授权博主） | ❌ 不能 | 抖音 `video.list` 只能读**授权给你的账号**；小红书**无内容 API** |
| **拉取内容**（合作博主） | ✅ 能（唯一合法路径） | 与博主签约后，让**博主本人授权你的应用**，走抖音 OAuth 拉其视频列表 |

**结论**：`搜索 + 跳转` 1.0 就能做（搜自建库）；`搜索 + 拉取抖音/小红书内容` 只对**已授权给你的合作博主**成立。网上的「拉取」教程基本都是爬虫，不采用。

**1.0 建议**：自建库（5 风格 + 10 妆教）+ CLI 搜索 + 跳转；同时启动博主授权合作，为二期「合法拉取」铺路。

### 产品决策 A：1.0 要不要做电商和商品推荐？

**建议：商品推荐＝做（"建议级"）；电商交易＝1.0 不做。**

| 做 / 不做 | 内容 | 理由 |
|---|---|---|
| ✅ 做「商品推荐（建议级）」 | 给**品类 + 关键成分 + 适配理由**（如"氨基酸洁面 + 2% 水杨酸精华"），可附具体产品示例 | 你已明确要推荐护肤品/化妆品；建议级不碰交易，合规成本低，且是后续变现的基础 |
| ❌ 1.0 不做「电商闭环」 | 不做商城、不做下单支付、不做返佣结算 | ①交易是重资产（供应链/履约/售后）；②化妆品功效宣称+广告法+返佣资质合规成本高；③**信任是这类产品的命脉**，过早带货会毁掉检测结果的可信度 |

**分期路线**：1.0 建议级推荐 → 1.5 接入持牌电商跳转（不自行履约）→ 2.0 具备资质后再考虑 CPS/精选联盟分佣。

### 产品决策 B：照片怎么处理？

**建议：1.0 走「上云分析 + 分析后即删 + 不落库 + 单独同意」，并预留端侧开关。**

|---|---|---|---|

| **上云 + 加密 + 分析后即删 + 不落库** | 高（可控） | 精度好、成本可控 | ✅ **1.0 采用** |
| 第三方视觉 API | 中（多一方经手） | 低成本快 | ⚠️ 需签数据处理协议，谨慎 |

要点：传输/存储加密、**处理完立即删除原图**、明示"单独同意"、不写入日志、不做人脸底库比对；`save_profile` 仅存**结论**（肤质/问题/偏好），不存照片。

### 产品决策 C：问卷会不会消耗用户耐心？（第四轮修订）

**结论变了：肤质分类从视觉段移除后，问卷从"可选兜底"升级为"必经 3 题"——所以更要做到极轻。**

- 题量锁死 **3 题**，全是单选、点击即走（实测预期 5–8 秒）
- 视觉段**先出结果**，问卷与照片展示并行，感知上不额外等待
- 每题给"不确定"选项，不强制；缺答也能出结论（`confidence=low`）
- 肤质结论由**确定性规则**算出，不花模型 token、不会幻觉
- 3 题各锁一个维度：紧绷→干、泛红→敏感、出油→油

理由：原先担心"问卷消耗耐心"，但用视觉换来的分类会翻车；**3 道单选的成本，远低于检测错误带来的信任损失**。

### 安全边界与降级策略

- **医疗边界**：任何"病名式"结论降级为"疑似…建议就医"；`compliance_check` 拦截诊断性表述
- **人脸隐私**：照片即删不落库；保存档案需单独同意；传输/存储加密；优先端侧预处理（二期）
- **内容版权**：内容来自③方 API，卡片必须带原作者与来源平台；⚠️ **合同必须有转授权/展示条款**，否则只放跳转链，不存文案
- **商品合规**：不夸大功效、不承诺效果、标注非广告；敏感成分（A醇/酸类）提示建立耐受与孕妇慎用
- **检测不准**：低置信度或图片质量差 → 提示重拍；仍不行 → 只用问卷结果 + 保守建议，不编造检测结论
- **内容缺失**：③方 API 超时/报错/空 → 降级本地 mock（≥3 个博主），**永不空手而归**
- **模型失败**：超时/报错 → 返回规则版方案模板

### 社群入口（微信群二维码）注意事项

- 微信**群二维码 7 天失效、满 100 人失效** → 必须用**企业微信"活码"**或动态二维码服务，不能写成死链
- `get_community_qr` 每次返回**当前有效**的码；过期自动轮换
- 埋点 `入群率`，作为留存指标的前置信号
- 合规：入群前放免责声明（不构成医疗建议）；群内不发布功效承诺

## Step 4.5 · 模型选型、成本预估与评测方案

### 关键约束：现有骨架不支持视觉

`scaffold/agent.py` 用的是 **Anthropic SDK + Anthropic-compatible 网关**，`.env.example` 里列的（MiniMax / GLM / Kimi / DeepSeek）**全是文本/代码模型，没有视觉能力**。皮肤分析必须多模态，所以要么换模型，要么加适配层。

### 推荐：两段式模型架构（视觉段 + 文本段）

| 段 | 任务 | 模型类型 | 推荐 | 理由 |
|---|---|---|---|---|
| 视觉段 | 只看图 → 结构化 JSON（肤质候选/可见问题/置信度/图片质量） | 小多模态 | 国内：Qwen-VL / 豆包 vision / GLM-4V；国际：Claude / GPT-4o-mini | 输出是短 JSON，小模型够用，便宜且快；**别把长推理塞进视觉调用** |
| 文本段 | 诊断 / 双方案 / 商品建议 / 风格匹配 / 妆教拆解 / 合规审核 | 强文本 | 复用骨架已支持的 DeepSeek / GLM / Kimi / Claude | **骨架零改造**，成本极低 |
| 兜底 | 视觉模型失败 | — | 规则版模板 | 保证降级可用 |

> 好处：只有「看图」这一步需要多模态，其余留在你已支持的 Anthropic-compatible 通道里，**改造面最小**。

> ❗ **实测排除**：GLM-4V 已用真实 key 试跑 → **不可用**（拿"图太暗"回避，或被逗后 7 张返回同一答案）。
> 豆包 `doubao-seed-evolving` 能用且**真的在读图**，但**中位 18s，超标**（P95 目标 15s）。
> 证据：`products/beauty_mirror/evals/vision/results/vision-provider-findings.md`。
>
> **对策**：把视觉调用与「3 道问卷」**并行**跑（用户答题 5–8s 可以掩盖大部分延迟），
> 或换 Qwen-VL 把延迟压到秒级。另：真实人像触发过智谱内容审核（`code 1301`），需保留降级。

### 成本预估（量级，非精确，以各官网为准）

单次完整会话 ≈ 1 次视觉调用 + 2~3 次文本调用。

| 环节 | 输入 | 输出 | 便宜档（国内） | 贵档（Claude 全流程） |
|---|---|---|---|---|
| 视觉 | ~1.5k 图 + 0.5k 提示 | ~0.4k JSON | ~¥0.005 | ~¥0.09 |
| 文本 ×3（方案/拆解/审核） | ~4k/次 | ~1.5k/次 | ~¥0.015 | ~¥0.15 |
| **单次合计** | | | **≈ ¥0.02** | **≈ ¥0.25** |
| 1000 次/日 | | | ~¥600/月 | ~¥7,500/月 |

**结论**：成本不是瓶颈。视觉模型选「能过评测的最便宜的那个」；预算更该花在**评测集**和**合规**上。

### 要不要做模型评测？——**要，且是 1.0 的第一优先级**

检测不准 = 后面全错 = 信任崩塌。而且仓库**已有现成评测框架**（`evals/forward/<case>/input.md + expected.json`，由 `blueprint` 模块跑，`tests/test_blueprint_engine.py` 已在用），**复用成本几乎为零**。

| 评测项 | 方法 | 通过线（建议） |
|---|---|---|
| **视觉准确度** | 50 张标注素颜照，只测**可见问题召回**（**不测肤质分类**） | **micro recall ≥ 0.80** |
| **置信度校准** | 低置信度样本是否真的更容易错 | 低置信区间错误率显著更高 |
| **合规拦截** | 对抗用例（「我是不是得病了」「推荐根治痘痘的」） | 拦截率 ≥95%，漏放 0 |
| **拆解质量** | 人工打分：步骤完整 / 可执行 / 不含功效承诺 | 抽样 30 条，均分 ≥4/5 |
| **成本与时延** | P50 / P95 端到端 | P95 ≤ 15s |

**落地**：新增 `evals/forward/beauty-mirror/`（沿用现有格式），把「模型选型」变成**可跑的对比**，而不是拍脑袋。

### 留存口径（第 4 问的建议）

建议**双指标**，主指标用 D7：

| 指标 | 定义 | 说明 |
|---|---|---|
| D1 回访率 | 首次使用后**次日**再次打开（任一行为） | 辅助：反映初始吸引力 |
| **D7 复访率（主）** | 7 日内 ≥2 次**核心行为** | **主指标** |
| 核心行为 | **再次检测** 或 **再次完成一个妆教跟练** | 二者取或 |
| 北极星变体 | 7 日内跟练完成 **≥3 次** | 护肤需要坚持，这个更贴近真实价值 |

理由：①皮肤改善周期是 2–4 周，**D1 太短，看不出价值**；②「打开」是弱信号，「再次跟练 / 再次检测」才是真需求验证。

参考基线（工具类，**本品尚无数据，仅作起步目标**）：D1 ≥25%、D7 ≥10%。
